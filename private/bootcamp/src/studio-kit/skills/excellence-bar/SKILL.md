# The Excellence Bar

This skill is enforcement, not aspiration. When it is active the bar applies to
the work itself, not to a description of the work.

The standard: every deliverable competes with the best paid alternative in its
class and wins on at least one axis the buyer can see. Not "good for the
budget." Not "good for a small business." Good, full stop.

## The five tests

Each one can be failed. Run all five before anything leaves.

1. **Ships as-is.** The recipient could use, send, print or publish it right
   now with zero edits. No placeholders, no TODOs, no "adjust to taste".
2. **Beats the alternative.** Hold it next to the best example of its class you
   can name. It must win somewhere specific: clarity, speed, finish, voice,
   completeness. If it loses everywhere, it is not done.
3. **Complete in its states.** Every state is designed: loading, empty, error,
   success, the edge case, the angry customer, the sold-out item. The happy
   path is the entry fee.
4. **Verified, not assumed.** Every claim is backed by having run it, rendered
   it, opened it, called it or printed it. "Should work" fails this test by
   itself.
5. **Unmistakably ours.** Someone who knows the business could name the maker
   with the logo covered. Voice, look and finish carry the signature.

## The loop

1. **Name the winner.** In two lines: the best example in the world of this
   kind of thing, and the three qualities that make it that. Build toward it.
2. **Build complete.** Real copy, real images, real data, every state. A
   beautiful shell with filler text is not a draft of excellence; it is a
   violation of it.
3. **Attack it.** Switch roles. You are the skeptical buyer who almost chose
   someone else. Find the five weakest things: the flat headline, the error
   message written by a compiler, the orphaned word, the chart with no units.
   Fix all five. Do not report them as caveats. Fixing them is the job.
4. **Verify for real.** Meet the work the way its recipient will. Open the page
   at phone width and desktop width. Render the PDF and read it. Place the
   test call and listen. Only claims that survived this step go in the report.
5. **Finish pass.** The details nobody asked for: the favicon, the share image,
   the empty-state sentence, the print margin, the 404 page.

## Forbidden shortcuts

Each of these, found in a deliverable or a report, means the work is not done:

- "Should work", "you may want to", "left as a starting point"
- Untested code presented as working
- Placeholder images, lorem ipsum, bracketed text, TBD, XX
- Error messages that expose internals or say "something went wrong" with no
  next step
- A PDF that is a printed web page instead of a designed document
- Skipping the attack pass because the first version seems strong
- Any phrase listed as banned in the rules file

## Before returning anything

1. Did I meet the work the way its recipient will, and can I cite the evidence?
2. Did I find and fix five weaknesses?
3. Is every state designed, or only the happy path?
4. Would this win against the best alternative on one visible axis?
5. Is there one sentence in my report that hedges about whether it works? If
   so, go verify and replace the hedge with the result.

If a missing password or decision blocks part of the work, build everything
that does not depend on it, state the assumption in one line, and name the one
thing needed.
